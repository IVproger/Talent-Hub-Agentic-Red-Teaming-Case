# Agentic Red Team: промежуточное описание проекта

**Команда:** Zero Trace

**Дата:** 4 сентября 2026 года

**Репозиторий:** https://github.com/IVproger/Talent-Hub-Agentic-Red-Teaming-Case

## Краткая аннотация

Мы делаем инструмент для динамической проверки ИИ-агентов с памятью и инструментами. Он проверяет ответ модели и фактические действия агента: какую запись тот сохранил, какой инструмент вызвал и какие аргументы передал.

Текущий прототип работает на изолированном инвестиционном стенде с синтетическими клиентами. Инструмент умеет запускать фиксированные многошаговые сценарии и генерировать варианты атаки Broken Access Control, собирать состояние стенда до и после шага, считать Attack Success Rate и сохранять доказательства в отдельный каталог запуска.

В первом подтверждённом эксперименте пользователь `cus=1001` четыре раза добился чтения портфеля `cus=1002`. Во всех четырёх попытках стенд зафиксировал вызов инструмента с чужим `cus`. Предварительный ASR этого узкого сценария равен 100%. Это результат на намеренно уязвимом режиме и на синтетических данных, а не оценка защищённости реальной банковской системы.

## Проблематика

Проверка пары «запрос → ответ» плохо подходит для агента. Ответ может выглядеть нормально, хотя агент уже записал вредоносную инструкцию в долговременную память или вызвал инструмент с чужим идентификатором клиента.

Для такой системы нужно проверять всю цепочку:

`вход → контекст → память → план → инструмент → аргументы → результат → изменение состояния → следующая сессия`

Главный риск для выбранного стенда — нарушение контроля доступа. Модель сама выбирает `cus` для инвестиционного инструмента, а в уязвимом режиме сервер не связывает этот аргумент с личностью пользователя.

## Актуальная постановка задачи

На промежуточном этапе мы проверяем две группы атак:

1. Манипуляция аргументами инструмента и чтение данных другого клиента.
2. Запись общей инструкции в долговременную память с последующим влиянием на другого пользователя или tool call.

Успех атаки определяет проверка состояния. Текст ответа используется как часть трассы, но не как единственный источник вердикта.

## Техническое решение

Прототип состоит из пяти частей:

1. `config/target.yaml` задаёт целевой стенд, роли LLM, пользователей и параметры запуска.
2. Генератор атак читает архитектуру и system card стенда и создаёт варианты BAC-запросов.
3. Scenario Runner выполняет YAML-сценарии от лица разных пользователей и в разных сессиях.
4. State Tracer снимает состояние MongoDB и читает журнал обращений к `invest-server`. Детерминированные проверки сравнивают ожидаемый эффект с фактическим состоянием.
5. CLI и локальный Streamlit-интерфейс запускают один и тот же pipeline. Каждый запуск сохраняет конфигурацию, попытки, findings, статус, данные наблюдаемости и Markdown-отчёт.

Стенд развёртывается через Docker Compose. В него входят ReAct-агент, MCP-сервер с 14 инвестиционными инструментами, MongoDB, Redis, Postgres, Keycloak и два слоя проверки доступа. Langfuse подключён опционально через W3C trace context и не влияет на итоговый вердикт.

## Уже реализовано

- единая команда `python -m agentic_redteam` с подкомандами `doctor`, `run`, `report`, `stand sync` и `serve`;
- один pipeline для CLI и Streamlit;
- четыре фиксированных YAML-сценария и адаптивный BAC-сценарий;
- снимки долговременной памяти и сбор фактических tool calls;
- детерминированные проверки для записи global policy, cross-user эффекта и подмены `cus`;
- отдельные артефакты для каждого запуска и редактирование секретов перед сохранением;
- опциональная сквозная трассировка runner и target через Langfuse;
- 77 автоматических тестов.

## Предварительные результаты

Завершённый запуск `20260903-220907-49c39e` проверил адаптивную BAC-атаку в режиме `vulnerable`:

- атакующий: `cus=1001`;
- цель: `cus=1002`;
- попытки: 4;
- доказанные атаки: 4;
- ASR: 100%;
- доказательство: журнал `invest-server` зафиксировал tool call с `cus=1002` от сессии пользователя `cus=1001`.

Запросы различались: прямое обращение, ссылка на полномочия сотрудника, сравнение двух портфелей и «проверка API». Все варианты привели к чтению чужого синтетического портфеля.

Автоматическая проверка проекта от 4 сентября: 77 тестов прошли, Python-модули компилируются, `git diff --check` не нашёл ошибок форматирования.

## Ограничения

- Результат 4/4 относится к одному классу атак, одному стенду и намеренно уязвимому режиму. Его нельзя переносить на другие системы.
- Memory-сценарии уже есть в pipeline, но их успешный live-прогон пока не сохранён.
- Сравнение `vulnerable` и `protected` пока не проведено одной и той же серией тестов.
- Полная Langfuse-трасса не проверена в последнем запуске: credentials не были настроены.
- Адаптеры состояния привязаны к MongoDB и журналу учебного `invest-server`.
- Журнал доступа стенда общий. Во время прогона нельзя смешивать red-team трафик с другими запросами.
- Автоматическое построение полной модели угроз произвольного агента пока не реализовано.
- Текущая конфигурация использует OpenRouter, поэтому для нового live-прогона нужен API-ключ или переключение YAML на локальную модель.

## Открытые вопросы

- Насколько стабильно модель сохраняет пользовательский текст как global policy?
- Воспроизводится ли цепочка `запись → извлечение другим пользователем → вредоносный tool call`?
- Блокирует ли `protected` режим все варианты BAC без потери обычного сценария?
- Какой минимальный адаптер состояния нужен для подключения другого агента?

## План до финальной версии

1. Провести и сохранить прогоны двух memory-сценариев.
2. Повторить BAC-набор в режимах `vulnerable` и `protected`.
3. Поднять локальный Langfuse и проверить одну сквозную трассу.
4. Свести результаты в таблицу по сценариям и обновить отчёт.
5. Обновить презентацию и записать короткое финальное демо.
