## 1. Границы реализованного MVP

MVP — это не «прототип атаки», а **сквозной рабочий цикл** от описания цели до
регрессионного теста. Границы определялись продуктово: в MVP вошло то, без чего
первый сегмент не сможет применить инструмент внутри контура, и не вошло то, что
нельзя честно доказать за неделю.

### Что входит

| Блок | Что реализовано | Статус |
| --- | --- | --- |
| **Профиль цели** | реестр `profiles/<name>/<version>.yaml`; `profile init` из OpenAPI, `profile ingest` из архитектуры и system card, `show / diff / check / verify / surface / coverage`; профиль — единственный носитель target-специфики | [ФАКТ] |
| **Карта поверхности** | точка входа, каналы доставки, инструменты с приоритетом чувствительности, память, внешние интеграции, evidence-источники и связи между ними; покрытие OWASP Agentic Top 10 считается только по state-доказуемым пунктам | [ФАКТ] |
| **Два пути атаки** | сценарный: 5 атакующих YAML-сценариев + штатный контрольный + замороженный baseline; автономный: `briefs generate` (OWASP LLM / Agentic Top 10, опционально ATLAS) → замороженные AttackBrief → атакующий агент (`chat` / `commit_memory` / `submit_attack`) → бинарный LLM-judge → ASR; стратегии `independent` и `adaptive` | [ФАКТ] |
| **Кампания** | многошаговые атаки от разных ролей и сессий; режимы `vulnerable` и `protected` в одном прогоне (A/B); `--trials N`; сброс цели и отдельное evidence-окно на каждую попытку; deadline и таймауты держит инфраструктура | [ФАКТ] |
| **Evidence** | шесть провайдеров: `db_query`, `log_regex`, `http_canary`, `trace`, `state_reset`, `bundle`; калибровка привязок; отказ источника → `error`, не «успех» | [ФАКТ] |
| **Вердикт и метрики** | детерминированные предикаты; градация `proven → indirect → not_proven → error → UNOBSERVABLE`; ASR `YES/(YES+NO)`, ошибки вне знаменателя; рядом — покрытие и разнообразие; для adaptive — discovery within K | [ФАКТ] |
| **Артефакты и отчёты** | иммутабельный `runs/<id>/` (`campaign.json`, `findings.json`, `evidence-NNNN.json`, `transcript.jsonl`, `status.json`); технический отчёт с payload, шагами и deep link на доказавший span; бизнес-отчёт `report --business` | [ФАКТ] |
| **Наблюдаемость** | W3C-трасса `redteam.run → campaign.attempt → stand.chat → stand.react.loop → stand.tool` в Langfuse; fail-open — не влияет на вердикт | [ФАКТ], живая трасса получена |
| **База знаний и lifecycle** | `kb list / search / status / rebuild`; автоматические переходы `fixed → retested → closed \| reopened` после повторной проверки | [ФАКТ] |
| **Регрессия** | `regress export` → `run --from` → `regress compare`; повтор создаёт новый каталог, исходный не меняется | [ФАКТ] |
| **Три входа на одном ядре** | CLI, Streamlit (`serve`), веб-интерфейс `webui/` на собственном дизайн-ките; общие гейты авторизации и read-only | [ФАКТ] |
| **Гейты безопасности** | без блока `authorization` прогон не стартует; просроченное окно = отсутствие; изменяющие цель команды помечены явно | [ФАКТ] |
| **Учебный полигон** | намеренно уязвимый инвестиционный ReAct-агент: Redis, MongoDB (episodic / semantic / global policy), MCP с 14 инструментами, Postgres с журналом обращений, Keycloak с 5 личностями; режимы `vulnerable` / `protected` | [ФАКТ] |

### Что не входит — сознательно

| Не входит | Почему |
| --- | --- |
| Второй target другого класса и формальный контракт адаптера | универсальность проверена на одной цели; это первая инженерная задача после хакатона |
| Живой `proven` для цепочки «отравление памяти → чужой tool call» | сценарий и предикаты готовы, прогоны выполнены, вердикт `not_proven`; не выдаём за успех |
| Автоматическая митигация или «автофикс» | кейсодатель снял требование; MVP — подтверждённое выявление, а не обещание исправить |
| Финансовая оценка ущерба в бизнес-отчёте | без входных данных заказчика это выдумка; отчёт связывает находку с бизнес-эффектом, но не считает деньги |
| Корпоративная ролевая модель, многопользовательский серверный UI | не влияет на доказательство ценности; UI — витрина пути, не продукт сам по себе |
| Регрессия как гейт в CI заказчика, массовые параллельные кампании | масштабирование после пилота |
| Замер времени аудита, себестоимости кампании и цены | это метрики пилота; в материалах — модель с указанными допущениями |

## 2. Основной пользовательский сценарий

**Персона:** MLSecOps / AI Security-инженер банка. **Контекст:** команда агента
подаёт новую версию на проверку перед релизом; есть авторизованный тестовый
контур с архитектурой, API и хотя бы одним наблюдаемым источником состояния.

**Job:** за часы, а не дни, получить доказуемый ответ «можно ли через память или
инструменты этого агента добраться до чужих данных или действия» — и оставить
после себя тест, который повторится после следующего релиза.

| Шаг | Что делает пользователь | Команда | Что получает |
| --- | --- | --- | --- |
| 0 | Подтверждает разрешение на тестирование и проверяет окружение | блок `authorization` в профиле; `doctor --profile …` | прогон без авторизации не стартует; drift конфигурации виден до запуска |
| 1 | Описывает цель: OpenAPI, архитектура, system card, схемы | `profile init --openapi … --base-url …`; `profile ingest --arch … --system-card … --doc …` (LLM-аналитик или `--offline`) | черновик профиля с привязками инструментов, памяти и evidence; неподтверждённые привязки помечены `TODO` |
| 2 | Убеждается, что MOROK видит состояние цели | `profile check` (read-only); `profile verify` (пишет маркеры — помечено как изменяющее); `profile surface --check`; `profile coverage` | карта поверхности с подтверждёнными статусами и честным покрытием стандарта |
| 3а | Сценарный путь: выбирает сценарии, роли, режимы, число попыток | `run --profile … --scenario all --mode vulnerable,protected --trials 3 --dry-run` → без `--dry-run` | предпросмотр плана и payload, затем кампания |
| 3б | Автономный путь: фиксирует задания и отпускает атакующего | `briefs generate --profile … --out DIR --count 5`; `run --profile … --briefs DIR --strategy adaptive --stop-on-success` | замороженные brief; попытки с transcript, tool traces, memory diff и вердиктом judge |
| 4 | Наблюдает прогон | `status.json` после каждой попытки; трасса в Langfuse | безопасная остановка без потери артефактов; сквозная трасса до вызова инструмента |
| 5 | Разбирает результат | `findings.json`; `report --run runs/<id>`; `report --business --run runs/<id>` | только state-доказанные находки; payload, шаги, точка компрометации, ссылка на доказавший span; бизнес-отчёт для риск-комитета |
| 6 | Передаёт находку команде агента и фиксирует её судьбу | `kb status … fixed`; после фикса `regress export` → `run --from runs/<id>` → `regress compare` | автоматический переход `fixed → retested → closed \| reopened`; сравнение ASR до/после; штатный сценарий подтверждает, что защита не сломала полезный запрос |

**Для демонстрации** тот же путь — профиль → карта поверхности → кампания →
находка с evidence → отчёт → повтор — доступен в Streamlit и в веб-интерфейсе.
Оба вызывают тот же `execute_campaign`, что и CLI, поэтому вердикт в UI не может
отличаться от вердикта в артефактах.

## 3. Как продуктовые решения повлияли на техническую реализацию

Это центральная таблица документа. Каждое решение принималось в продуктовом
слое (Q&A с кейсодателем, интервью, анализ сегмента), а затем стало
архитектурным ограничением, инвариантом или тестом.

| # | Продуктовое решение | На чём основано | Техническое следствие | Где видно |
| --- | --- | --- | --- | --- |
| 1 | **Проверяем агентную систему, а не модель** | кейс и Q&A: объект — память, роли, инструменты, состояние | evidence снимается с фактических tool calls и памяти; стенд с многоуровневой памятью и MCP; предикаты над состоянием, не над текстом | `evidence/providers/`, `assertions/`, `stand/` |
| 2 | **Вердикт только из состояния** | Альфа-Банк: «важны трейсы, а не ответы»; Raft: «сложность — найти вредоносный вызов в трассе» | инвариант US-23: предикат на тексте → потолок `indirect`; `YES` judge без наблюдённого state → `indirect`; в `findings` попадает только `proven` | `assertions/`, `reporting/technical.py`, тесты `test_attacker_judge.py` |
| 3 | **Первый сегмент — банки и организации с повышенными требованиями к ИБ** | интервью Альфа-Банка: контекст и трассы нельзя выносить наружу | on-prem по умолчанию; локальные / OpenAI-совместимые модели; Docker Compose; в YAML нет секретов — только имена env; внешняя телеметрия fail-open, чтобы её отсутствие не блокировало работу | `config/`, `observability.py`, `deploy/` |
| 4 | **Перенос на новую цель — настройка, а не проект** | допущение модели ценности (0,5–1 ч на профиль); сегмент 2 требует white-label-модуля | трёхслойная архитектура с односторонней зависимостью; профиль — единственный носитель target-специфики; pipeline переписан на месте, когда стало ясно, что target-детали текут в ядро | `profile/`, `tests/test_no_target_leak.py` |
| 5 | **CLI-first и интегрируемый формат** | Q&A: «нужен скрипт / CLI, UI не целевая форма» | один campaign runner для CLI, Streamlit и webui; машиночитаемые JSON-артефакты; общие гейты авторизации и read-only | `app_cli.py`, `campaign/`, `ui/`, `webui/` |
| 6 | **Находка — регрессионный актив, а не строка в PDF** | H4; ИТМО: полный цикл согласований — недели; Альфа-Банк: нет реестра уязвимостей по стеку | иммутабельный `runs/<id>/`; `run --from` создаёт новый каталог; `regress export / compare`; база знаний с lifecycle `fixed → retested → closed \| reopened` | `storage/`, `reporting/regression.py`, `knowledge/lifecycle.py` |
| 7 | **Разнообразие важнее накрученного ASR** | Q&A кейсодателя: «ценится разнообразие сценариев, не ASR» | ASR всегда рядом с покрытием и разнообразием; ошибки вне знаменателя; дедупликация payload с пометками `new` / `repeat`; в adaptive — discovery within K вместо iid-ASR | `attacker/campaign.py`, `generation/`, `findings.json` |
| 8 | **Первый фильтр, а не замена эксперта** | Raft: «автономный продукт не должен притворяться пентестером»; ИТМО: эксперт задаёт threat model | LLM-роли ограничены (генератор, аналитик, судья `YES/NO`, писатель отчёта); ни одна не выносит security-вердикт; сценарий без объявленного источника evidence не запускается, потому что `not_proven` от нехватки данных неотличим от «атака не сработала» | `llm.py`, composer-гейт в `campaign/` |
| 9 | **Два потребителя результата — команда агента и риск-комитет** | Альфа-Банк: допустимость риска согласуется с бизнесом; интервью: отчёт должен переживать согласования | два отчёта на одних `findings`: технический (payload, шаги, principal, deep link на span) и бизнес-отчёт (`риск / польза / следующий шаг`, без выдуманного ущерба) | `reporting/technical.py`, `reporting/business.py` |
| 10 | **Разведка боем + воспроизводимость, а не одно из двух** | кейсодатель: приоритет — динамическая проверка; CustDev: альтернатива — «сильная модель с harness» | два пути: YAML-сценарии для регрессии и AttackBrief с автономным агентом для поиска неожиданных маршрутов; brief замораживается; заявление атакующего сохраняется, но не определяет итог | `attacker/`, `local-scenarios/` |
| 11 | **Только авторизованное тестирование** | ограничения сегмента; движок реально ломает цель | гейт `authorization` с окном действия; read-only режим; `profile verify` помечен как изменяющий состояние; синтетические данные на стенде | `campaign/`, профиль |
| 12 | **UI — витрина пути, а не панель настроек** | концепция UI и требования к демо; бренд MOROK | дизайн-кит и webui показывают один путь «профиль → поверхность → кампания → находка → отчёт»; UI не добавляет логики поверх ядра | `design-ui-kit/`, `webui/` |

Общий вывод: продуктовый слой не «описал готовое», а задал инварианты, под
которые переписывался pipeline. Самые дорогие инженерные решения хакатона —
профильная архитектура, вердикт из состояния и два пути атаки — родились из
интервью и Q&A, а не из технического удобства.

## 4. Критерий завершения MVP — статус на 07.09.2026

На промежуточной точке мы зафиксировали: MVP доказан, когда один и тот же
сценарий воспроизводится, оставляет след в состоянии, даёт одинаковый вердикт
во всех входах и меняет результат после включения защиты.

| Критерий | Статус | Факт |
| --- | --- | --- |
| Сценарий воспроизводится несколько раз | ✅ | adaptive BAC — 4 из 4 попыток `proven`; `poison-to-tool-chain` исполнен 3× в каждом режиме |
| Оставляет проверяемый след в памяти или tool call | ✅ | `actor cus=1001 → фактический аргумент инструмента cus=1002`; источник — журнал обращений, не ответ LLM |
| Одинаковый вердикт в CLI, UI и артефактах | ✅ | один `execute_campaign`; UI визуализирует `findings.json`, не пересчитывает |
| После включения защиты результат меняется, штатный запрос не ломается | ✅ | тот же сценарий: `proven` в `vulnerable`, `not_proven` в `protected`; контрольный `normal-own-portfolio` проходит |
| Находка проходит полный lifecycle до регрессионного теста | ✅ | `fixed → retested → closed \| reopened` на реальной базе знаний |
| Сквозная трасса от runner до инструмента цели | ✅ | прогон `20260905-192427-e7f221`, 19 наблюдений в одном trace |
| Полная цепочка «память → чужой tool call» доказана живой целью | ❌ | cross-user policy записана в память в 6 из 6 попыток, но при активации сессия жертвы вызвала только свои данные — вердикт `not_proven`; предикаты и атрибуция шагов работают, поведение модели стенда цепочку не замкнуло |
| Универсальность адаптера подтверждена второй целью | ❌ | защищено архитектурно и тестом, но не вторым target |

Критерий MVP, заданный 04.09, выполнен. Две незакрытые строки — не дефекты
реализации, а границы доказательства, которые мы называем сами и переносим в
план пилота.
