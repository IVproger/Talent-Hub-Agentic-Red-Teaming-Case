# Идея

Baseline сегодня для аудита безопасности агентов — любой харнесс с хорошей моделью и доступом к нужным инструментам. Такой сетап уже может часами крутить сценарии, анализировать ответы агента, читать память и трейсы, вызывать инструменты и пробовать варианты атак.

Но использовать его как полноценный корпоративный инструмент пока нельзя. Не хватает:

1. Верифицируемости — независимого подтверждения результата. Успех атаки не должен быть мнением атакующего агента. Отдельный Evidence Engine проверяет фактические изменения: запись в память или БД, вызов tool и его аргументы, изменение внешнего состояния, влияние на следующую сессию или другого пользователя.

2. Базы знаний возможных атак — классификации атак на память, инструменты и состояние агента. Для каждой атаки нужны предпосылки, возможные каналы доставки, этапы, ожидаемый эффект, success criteria и способы сбора evidence. База может опираться на MITRE ATLAS, OWASP, научные статьи и собственные сценарии банка.

3. Воспроизводимости — возможности показать, что из конкретного начального состояния, на конкретной версии агента, с определёнными сценарием и конфигом атака привела к конкретному результату. Для этого нужны фиксация исходного состояния, snapshots, полный лог выполнения, reset окружения и replay.

4. Наблюдаемости — единого формата трейсов, связывающего пользовательский ввод, действия атакующего харнесса, ответы целевого агента, чтение и запись памяти, tool calls, изменения аргументов и итоговый эффект.

5. Отчётности — ASR по отдельным сценариям и семействам атак, найденные уязвимости, evidence, трейсы, критичность и условия воспроизведения. Отчёт должен показывать не только финальный ответ, но и точное место компрометации: запись в память, retrieval, принятие решения или вызов инструмента.

Предлагаю CLI-надстройку, не зависящую от конкретного харнесса.

Пользователь задаёт конфиг: описание атакуемого агента, API-контракт, доступные роли и инструменты, архитектуру памяти, сценарий атаки, success criteria, источники трейсов и правила очистки состояния. Это может делать и research-агент, который в цикле анализирует систему и генерирует новые сценарии и конфиги.

Затем запускается атакующая сессия через любой поддерживаемый харнесс: pi, Codex, Claude Code или отдельного LLM-агента. Харнесс отвечает за стратегию атаки и выбор следующего шага, но не определяет её успех.

Независимые collectors параллельно собирают evidence: API-запросы, трейсы, tool calls, snapshots и diff памяти или БД. После сессии Verdict Engine проверяет success criteria и выносит результат: атака доказана, подтверждена косвенно или не доказана.

На выходе:

- машиночитаемый JSON с findings для интеграции с корпоративными системами;
- HTML-отчёт с ASR, evidence и timeline атаки;
- replay-конфиг для повторного запуска;
- regression-сценарий для проверки следующей версии агента.

Решение может работать в нескольких режимах. В black-box доступны только API агента и поведенческие признаки; в gray-box — также трейсы; в white-box можно напрямую проверить изменения памяти, БД и внешнего состояния. Один и тот же сценарий должен запускаться во всех режимах, но с разным уровнем доказательности.

Пайплайн удобно встроить в CI/CD и использовать как security regression testing. Один раз найденная атака становится воспроизводимым тестом, автоматически проверяемым при изменении модели, промптов, архитектуры памяти, инструментов или ролевой модели.

Мы не пытаемся сделать ещё один атакующий харнесс, а делаем недостающий слой вокруг существующих: стандартизируем сценарии, фиксируем состояние и трейсы, независимо доказываем результат и превращаем отдельные эксперименты агентов в управляемый корпоративный аудит.
